논리적 오류 효율적 점검 방법론

대규모 임베디드 펌웨어(12+ 백엔드 모듈, 5 태스크, 7 프론트 모듈)를 체계적이고 반복 가능하게 점검하는 프레임워크입니다.

---

📋 개요: 3단계 접근법

```
[1단계] 자동 분석 (도구)     ← 즉시 실행, 기계적 오류 90% 발견
    ↓
[2단계] 패턴 검색 (grep)     ← 수동, 알려진 함정 패턴
    ↓
[3단계] 카테고리별 리뷰      ← 수동, 논리적/아키텍처 오류
    ↓
[4단계] 회귀 방지 (자동화)   ← 지속, 재발 방지
```

소요: 1단계 1~2일, 2단계 반나절, 3단계 2~3일, 4단계 지속

1.2. cppcheck — 정적 분석

설치:

```bash
# Windows: choco install cppcheck
# macOS: brew install cppcheck
# Linux: apt install cppcheck
```

실행:

```bash
cppcheck --enable=all \
         --inconclusive \
         --std=c++17 \
         --platform=unix32 \
         --suppress=missingIncludeSystem \
         --inline-suppr \
         --template="{file}:{line}: [{severity}] {id}: {message}" \
         --output-file=cppcheck.log \
         src/
```

주요 탐지 항목:

카테고리 예시

memleak 메모리 누수
unusedVariable 미사용 변수
knownConditionTrueFalse 항상 참/거짓 조건
duplicateCondition 중복 조건
invalidPointerCast 잘못된 포인터 캐스트
shiftTooManyBits 시프트 오류
redundantAssignment 불필요한 대입

🔍 2단계: 패턴 검색 (grep) — 30분

알려진 함정 패턴을 코드베이스 전체에서 검색.

2.1. 시간 관련 오류 (최우선)

millis() wrap-around:

```bash
# 위험: signed 비교
grep -rn "millis()" src/v0410/ | grep -v "uint32_t\|int32_t\|int64_t"

# 위험: 직접 비교 (wrap 시 오류)
grep -rn "if.*millis()\s*[<>]" src/v0410/

# 안전 패턴: (now - start) < timeout  → 확인
grep -rn "(uint32_t)millis() - " src/v0410/
```

주의:

```cpp
// 위험 (wrap 시 오류)
if (millis() > lastMs + timeout) { ... }

// 안전
if ((uint32_t)(millis() - lastMs) > timeout) { ... }
```

2.2. 문자열 안전성

```bash
# 위험 함수
grep -rn "strcpy\|sprintf\|strcat\|gets\|scanf" src/v0410/

# 안전 함수 확인
grep -rn "strlcpy\|strlcat\|snprintf" src/v0410/ | wc -l
```

2.3. 동적 할당

```bash
grep -rn "malloc\|calloc\|realloc\|free\|new \|delete" src/v0410/
```

ESP32 임베디드에서는 동적 할당 최소화 원칙.

2.4. 큐 반환값 무시

```bash
# xQueueSend 결과 무시
grep -rn "xQueueSend\|xQueueReceive\|xSemaphoreTake" src/v0410/ | grep -v "==\|!=\|if\|return"
```

2.5. 상태 변수 접근 (락 없이)

```bash
# 공유 상태 변경 지점
grep -rn "_state\." src/v0410/ | grep "=" | grep -v "_lock"
grep -rn "_cfgProfile\." src/v0410/ | grep "=" | grep -v "_lock\|Snapshot"
```

2.6. Switch break 누락

```bash
# default 없는 switch (Wswitch-default로 컴파일러가 잡음)
grep -rn "switch" src/v0410/*.cpp | head -50
```

2.7. volatile 누락

```bash
# ISR/태스크 간 공유 플래그
grep -rn "_req\|_flag\|_pending\|_active\|_busy" src/v0410/*.h | grep -v "volatile\|static"
```

2.8. 배열 인덱싱

```bash
# 상수 인덱스 접근
grep -rn "\[[0-9]\+\]" src/v0410/*.cpp | grep -v "//\|G_\|EN_"
```

2.9. = vs == 오타

```bash
grep -rn "if.*[^=!<>]=[^=]" src/v0410/ | grep -v "==\|!=\|<=\|>=\|+=\|-=\|*=\|/="
```

2.10. 초기화 순서

```bash
# 초기화 함수 호출 순서
grep -rn "\.begin(" src/v0410/ | sort
```

📊 3단계: 카테고리별 수동 리뷰 — 2~3일

3.1. 카테고리 1: 시간 기반 로직 (최우선)

점검 항목:

항목 확인 방법
millis() wrap (49.7일) 모든 시간 비교에 (uint32_t)(now - start) 사용
micros() wrap (71분) 위와 동일
vTaskDelay(0) 무한 루프 방지
xTaskGetTickCount() tick 기반 계산
시간 기반 상태 전이 초기값, 리셋 조건

점검 스크립트:

```bash
# 시간 관련 함수 사용 지점 전수
grep -rn "millis\|micros\|vTaskDelay\|xTaskGetTickCount" src/v0410/ | \
    awk -F: '{print $1":"$2}' > time_points.txt
```

3.2. 카테고리 2: 동시성 (FreeRTOS)

점검 항목:

항목 확인 방법
태스크별 상태 소유권 SPEC §3.3 대조
락 순서 (데드락) _lock() 중첩 확인
큐 overflow xQueueSend timeout=0 시 drop 확인
volatile 태스크 간 공유 플래그
초기화 순서 태스크 생성 vs 큐 생성 순서

점검 매트릭스 (예시):

```
변수              | Reader      | Writer      | 보호

_activeMode       | all         | sensor      | volatile

3.3. 카테고리 3: 상태 머신

점검 항목:

항목 확인 방법

점검 방법 — 상태 전이표:

예: C20_BtnDispatcher phase FSM

```
From        | Event         | To          | Action

3.4. 카테고리 4: 경계값

항목 예시

커버리지 불균일 전원 관리는 C-1~C-5 세분화, 문서 체계는 미점검
이전 결정 참조 안 됨 Motion Advanced 이후 Power에서 _snapshotRuntimeToE10Config 백업/복원을 다시 지적
컨텍스트 유실 대화 턴 사이에 이전 계약(예: _macroAbortToken)이 소실
분류 일관성 없음 때로 C/H/M, 때로 N/I, 때로 Phase

근본 원인 3가지:

1. 소스 전체가 매 리뷰마다 재해석 — 계약(contract)이 문서화되지 않음
2. 커버리지 기준이 없음 — "이번엔 뭘 봐야 하나?"가 임의적
3. 산출물이 대화에만 존재 — 파일로 남지 않아 다음 리뷰 시 재구성

---

🎯 제안: 계약 기반 리뷰 (Contract-Based Review)

핵심 아이디어

"소스 전체를 매번 보내지 않는다. 5개 지속 산출물(persistent artifacts)로 리뷰한다."

```
[프로젝트 루트]
├── docs/
│   ├── CONTRACT.md      # 모듈 경계 계약 (인터페이스)
│   ├── STATE.md         # 상태 소유권 + FSM
│   ├── FLOW.md          # 기능별 데이터 흐름
│   ├── BUDGET.md        # 시간/자원 예산
│   └── SPEC.md          # 요구사항 (00.SPEC_0410_001.md)
```

리뷰 요청 시:

```
[Feature X 리뷰]
- 5개 산출물 + Feature X의 .h/.cpp 만 전달
- "CONTRACT.md 기준 위반 + STATE.md 소유권 위반 + BUDGET.md 초과" 순으로 검토
```

효과: 매 리뷰가 동일 기준 + 국소 범위로 수렴

📋 5개 지속 산출물 상세

1. CONTRACT.md — 모듈 경계 계약

목적: 모든 인터페이스(함수/큐/공유 변수)를 한 표에 고정

템플릿:

```markdown
## 함수 계약
| 함수 | 호출자 | 컨텍스트 제한 | 부수효과 | 실패 시 |
|---|---|---|---|---|
| `_startMacro(idx)` | commTask only | 블로킹 금지 | `_macroState` 갱신 | 로그 후 return |
| `_resolveSlot(mode,t)` | sensorTask, commTask | – | 락 획득 | NONE 반환 |
| `switchProfile(idx)` | web task | 진행 중 재진입 금지 | 큐 드레인 + HID release | false |

## 큐 계약
| 큐 | Producer | Consumer | Size | Timeout | Overflow 정책 |
|---|---|---|---|---|---|
| `_qFrame` | sensorTask | commTask | 1 | overwrite | 최신 유지 |
| `_qActionExec` | sensorTask/web | commTask | 8 | timeout=0 | drop |
| `_qHidCmd` | web | commTask | 4 | timeout=0 | drop |

## 공유 변수 계약
| 변수 | Writer | Reader | Sync | 원자성 근거 |
|---|---|---|---|---|
| `_macroAbortToken` | any | commTask | 없음 | uint32 증가만 |
| `_btnLDown` | sensorTask | sensorTask | 없음 | volatile bool |
| `_cfgProfile` | web (write), all (read) | 락 | `_mutex` | – |
```

효과: 새 기능 추가 시 어느 계약을 위반하는지 즉시 확인 가능

---

2. STATE.md — 상태 소유권 + FSM

목적: 모든 상태 변수 + 상태머신을 표로 고정

템플릿:

```markdown
## 소유권 매트릭스 (요약)
| 상태 | 소유자 | 읽기 허용 | 동기화 |
|---|---|---|---|
| `_freezeState` | sensorTask | – | – |
| `_snapActiveAxis` | sensorTask | – | – |
| `_macroState.active` | any | any | volatile |
| `_hid` | commTask | – (isConnected read만) | – |

## FSM 명세
### Click-Freeze FSM
| 상태 | 진입 조건 | 이탈 조건 | 부수효과 |
|---|---|---|---|
| IDLE | (기본) | btnDown && |ω|<th | `_freezeTimer=0` |
| LOCKED | IDLE → btnDown | UP / timeout / |ω|>th | fx=fy=0 |
| HOLD | LOCKED → UP | hold_timer ≥ 20ms | fx=fy=0 |
| FADEOUT | HOLD → 20ms | fade ≥ 30ms | scale 감쇠 |
```

효과: 새 상태 추가 시 누락/중복 즉시 발견

---

3. FLOW.md — 기능별 데이터 흐름

목적: 각 기능의 파이프라인 + 실패 경로를 그림으로 고정

템플릿:

```markdown
## 모션 파이프라인 (sensorTask 내부)
[MPU raw] → [EMA] → [Zero Snap] → [Sigmoid] → [DPI] → [Precision]
          → [Snap] → [Click-Freeze] → [_qFrame] → HID

실패 경로:
- NaN 감지 시 → `_recoverI2C()` → 다음 tick continue
- 락 획득 실패 시 → `_errMutexMiss++`

## 프로파일 스위치 (web task)
[web POST] → `switchProfile(idx)` →
  ├─ `_macroAbortToken++`
  ├─ 큐 드레인 (_qActionExec, _qHidCmd)
  ├─ `_reqResetBtnDisp = true` (sensorTask 위임)
  ├─ `forceReleaseButtons()` (큐 경유)
  ├─ `_reloadActiveProfile()` (락)
  └─ LED flash
```

효과: 새 기능 통합 시 기존 흐름과의 간섭 즉시 확인

---

4. BUDGET.md — 시간/자원 예산

목적: 모든 태스크 주기 + 함수 worst-case 시간 명시

템플릿:

```markdown
## 태스크 예산
| 태스크 | 주기 | Worst-case 실행 시간 | 여유 |
|---|---|---|---|
| sensorTask | 8ms | ~4ms (측정) | 4ms |
| commTask | 7ms | ~3ms | 4ms |
| ledTask | 50ms | ~1ms | 49ms |

## 블로킹 지점
| 함수 | 위치 | 최대 블로킹 | 영향 |
|---|---|---|---|
| `_runGyroCalibration` | sensorTask | 1000ms | commTask 지연 |
| `vTaskDelay(_kbTapMs)` | commTask | 22ms | 커서 프레임 지연 |
| `_runMacro` | (구) commTask | 16s | **해결됨 (C-3)** |

## 데드라인 위반 조건
- sensorTask: 8ms 초과 → 커서 jitter
- commTask: 7ms 초과 → HID latency
- 매크로 실행: 모든 step ≤ 2000ms
```

효과: 새 기능이 기존 여유를 초과하는지 즉시 판정
