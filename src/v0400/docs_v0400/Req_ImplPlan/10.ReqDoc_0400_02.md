

# 사용자 개별화 기능 고도화 — 검토

## 1. 현재 개인화 수준 (실측)

| 항목 | 현재 | 
| --- | --- | 
| Mode | 3개 (PC/PPT/TV) | 
| 슬롯/Mode | 27개 (S1~S15 + flick4 + linear4 + tilt4)
| 총 슬롯 조합 | 3 × 27 = 81개 | 
| 액션 종류 | ~40종 (Mouse/KB/Consumer/Special) | 
| 세부 파라미터 | ~30개 (감도, 임계, 시간, 필터)
| Multi-Host | 3 peer | 
| Config | 단일 파일 (config_0400.json ~6-8 KB) | 

판단: 단일 사용자 관점에선 이미 충분. 개별화 여지는 3축으로 확장 가능.

---

## 2. 개별화 확장 축 (3개)

| # |  축 | 동기 | 비용 | 리스크 | 
| --- | --- | ---  |  --- | --- | 
| A |  프로파일 세트 (다중 설정) |  다중 사용자 / 상황별 | 中 | 저장공간 | 
| B | 매크로 (액션 시퀀스) | 복합 동작 | 中 | Config 크기 | 
| C | 슬롯 프리셋 (재사용 스니펫) | 재입력 절약 | 小 | UX 복잡 |

## 3. 각 축 상세

### 🟢 A. 프로파일 세트 (권장)

#### 개념:

```
현재: config_0400.json  (단일)
확장: profiles/
      ├── active.json       (활성 프로파일 선택)
      ├── profile_A.json    (사용자 A / 업무용)
      ├── profile_B.json    (사용자 B / 게임용)
      └── profile_C.json    (사용자 C / 발표용)
```

#### 기능:
- 프로파일 N개 (예: 최대 5개)
- 각 프로파일 = 독립된 modes[3] + 튜닝 파라미터
- 전환 트리거:
    - 버튼 조합 (예: Side R 3초 + Top R 클릭)
    - 웹 UI
    - (선택) 시간 스케줄
    - 저장: active 프로파일만 RAM 로드

#### 비용:

- 저장공간: 8KB × 5 = 40 KB (LittleFS 여유 충분)
- RAM: active 프로파일만 (~8KB) → 무영향
- 코드: C10_Config 확장 (~200줄)
- UI: 프로파일 관리 탭 추가

#### 리스크:

- 프로파일 전환 시 Mode/진행 액션 해제 필수 (stuck 방지)
- active 프로파일 잃어버리면 부팅 실패 → boot_state에 active index 저장

#### 장단점:

- ✅ 명확한 동기 (다중 사용자/상황)
- ✅ 실현 가능 (기존 config 로직 확장)
- ⚠️ 웹 UI 복잡도 증가

#### 실현 시나리오:

```
아침: PC Mode 1로 업무 (프로파일 "Office")
저녁: 게임 (프로파일 "Gaming") — DPI/가속 다름
발표: 프로파일 "Present" — Mode 2 슬롯 커스텀
```

---

### 🟢 B. 매크로 (액션 시퀀스)

개념:

```
현재: 슬롯 = 단일 액션
확장: 슬롯 = 액션 N개 + 각 사이 딜레이
```

Config 표현:

```json
"slots": [
  {
    "seq": [
      { "k": 4, "p16": 6, "p32": 1, "delayMs": 0 },     // Ctrl+C
      { "delayMs": 80 },                                 // 대기
      { "k": 4, "p16": 25, "p32": 1, "delayMs": 0 }     // Ctrl+V
    ]
  }
]
```

비용:

- Config 크기: 슬롯당 ~5배 (평균 2~3 액션)
- 실행: _actExec에 시퀀서 추가 (~100줄)
- UI: 시퀀스 편집기 (드래그/추가/삭제)

리스크:

- 딜레이 동안 커서 지연 (H-5와 유사)
- 매크로 중 취소 어려움

장단점:

- ✅ 강력한 표현력
- ⚠️ UI 구현 비용 큼
- ⚠️ H-5 이슈 악화

권장: 2차 도입. A 먼저 안정화 후.

---

### 🟡 C. 슬롯 프리셋 (스니펫)

개념:

```
웹에서 슬롯 하나를 편집 → "저장" 클릭
  → 프리셋 목록에 추가 (예: "Ctrl+Alt+Del", "Alt+Tab 매크로")
  → 다른 슬롯에 "불러오기"
```

비용:

- 저장: 프리셋 N개 (프로파일과 별개)
- UI: 프리셋 관리 + 슬롯에 적용 버튼
- 코드: 거의 없음 (UI만)

장단점:

- ✅ UX 편의
- ⚠️ 개별화라기보다 편집 편의

권장: A 도입 시 함께. 하지만 독립적으론 우선순위 낮음.

## 4. 자원 예산 재점검

| 자원 | 현재 | A 도입 시 (5 프로파일) | 
|  --- |  --- |  --- | 
| Flash | 45% (1.42 MB) | +2~5 KB (코드) | 
| RAM | 40% (131 KB) | +~10 KB (프로파일 관리) | 
| LittleFS config |  ~6-8 KB | 40 KB | 
| LittleFS 여유 | ~1.5 MB (default_4MB partitions) | 여유 | 
| Config body max | 8 KB | 8 KB 유지 (프로파일당) | 
| 부팅 시간 | ~8.5초 (grace) | +0.2초 | 

결론: 자원 문제 없음.

## 5. 추천 조합

이유:

- 실기 리스크 낮음

### 2차 (A 안정 후)

B (매크로) + C (프리셋)

이유:

- 표현력 확장
- A의 프로파일 구조 위에 자연스럽게 얹힘

## 6. A 도입 시 설계 요약

### 6-1. 파일 구조

```
/json/
├── config_0400.json          (레거시 — 프로파일 시스템 도입 시 프록시)
├── active_profile.json       (활성 프로파일 index + 이름)
├── profiles/
│   ├── profile_0.json        (Office)
│   ├── profile_1.json        (Gaming)
│   ├── profile_2.json        (Present)
│   ├── profile_3.json        (TV)
│   └── profile_4.json        (Spare)
└── boot_state_0400.json
```

### 6-2. 전환 트리거

트리거 동작
버튼 조합 (Side R 3초 + Top R 클릭) 다음 프로파일 순환
웹 UI 프로파일 선택
(선택) Mode 전환과 동시 특정 Mode 진입 시 프로파일 연동

### 6-3. 전환 시 안전 처리

```
1. 진행 중 액션/repeat 해제 (`_actExec.releaseAll()`)
2. 디스패처 리셋 (`_btnDisp.resetAll()`)
3. 제스처 리셋 (`_gesture.reset()`)
4. ForceRelease
5. 신규 프로파일 로드 (`loadAll`)
6. `_applyE10ToRuntime`
7. LED: 흰색 3회 flash (전환 표시)
```

### 6-4. 웹 UI

Dashboard 탭에 추가:

```
[Profile] [Office ▼]  [전환] [복제] [이름변경] [삭제]
```

신규 탭 (또는 기존 Config 탭 확장):

- 프로파일 목록
- 각 프로파일의 modes 매트릭스 (기존 Mode Slots 탭 재사용)
- 공통 파라미터 vs 프로파일별 파라미터 구분

### 6-5. API 확장

| Method | Endpoint | 용도 | 
| - | - | - | 
| GET | /api/profiles | 목록 + 활성 index | 
| POST | /api/profiles/switch | 활성 전환 | 
| POST | /api/profiles/create | 복제 생성 | 
| POST | /api/profiles/rename | 이름 변경 | 
| POST | /api/profiles/delete | 삭제 | 
| GET | /api/profiles/{n}/config | 프로파일 config 조회 | 
| POST | /api/profiles/{n}/config | 프로파일 config 저장 | 

### 6-6. 공통 vs 프로파일별 필드

공통 (모든 프로파일 공유):

- WiFi 설정
- LED 밝기
- Sleep idle timeout
- SafeBoot state

프로파일별:

- DPI / 감도 / 임계값
- Precision / 제스처 / Front Hold 파라미터
- Active Mode / 슬롯 매트릭스
- Active peer index

권장: A 단독으로 시작.

# 웹 페이지 기반 사용자 개별화 — 고도화 검토

## 1. 현재 웹 개별화 수준 (실측)

| 사용자가 웹에서 조작 가능 | 불가능 | 
| --- | --- | 
| 슬롯별 Action 선택 (kind + p16 + p32) | 슬롯 → 트리거 변경 | 
| Mode 1/2/3 각각 편집 | 트리거 자체 추가 (새 조합) | 
| DPI / Precision / 임계값 파라미터 | 매크로 (다중 액션) | 
| LED 밝기 | 새 Action kind 추가 | 
| SafeBoot / OTA / Rollback | 프로파일 전환 | 

결론: 트리거는 하드코딩, Action만 선택 가능. 사용자 자유도가 "절반".

## 2. 개별화 3축 (Button / Gesture / Action)

| 축 | 현재 | 확장 여지 | 
| --- | --- | --- | 
| Button | 트리거 고정, Action만 | 트리거 ↔ Action 완전 자유 매핑 | 
| Gesture | 트리거 고정, Action만 | 트리거 ↔ Action 자유 + 커스텀 임계 | 
| Action | kind별 고정 폼 | 매크로 / 커스텀 시퀀스 |

## 3. 웹 UI 구성 옵션 (3단계)

### Option 1 — 확장형 슬롯 편집기 (최소 침습)

```
[Mode Slots 탭 확장]
┌────────────────────────────────────────────┐
│ Mode: [1: PC] [2: PPT] [3: TV]             │
├────────────────────────────────────────────┤
│ S1: [Top L Click ▼] → [Mouse L Click ▼]   │
│ S2: [Top L Double ▼] → [Alt+Tab      ▼]   │
│ S3: [Top L Long ▼]   → [없음        ▼]   │
│ ...                                        │
└────────────────────────────────────────────┘
```

**특징**:
- 좌측 = 트리거 select, 우측 = Action select
- 트리거 목록: 20여 개 (S1~S15 + Flick 4 + Linear 4 + Tilt 4)
- 트리거끼리 중복 배정 검증
- Action은 기존 UI 재사용

**비용**:
- 웹 UI: 슬롯 매트릭스에 트리거 컬럼 추가
- 백엔드: 트리거 인덱스도 config에 저장
- 기존 slots[] 배열 순서 고정 폐기 → {trigger, action} 쌍 배열

**장점**:
- 실현 명확, UX 친숙
- 사용자 자유도 "완전"

**단점**:
- slots[] 스키마 변경 → 기존 config 마이그레이션
- 검증 로직 복잡 (트리거 중복, 필수 트리거 잠금)

## 4. 트리거 자유도의 세부 옵션

Option 1 채택 시, 트리거를 어디까지 열어줄까?

### Tier A — 기존 트리거 재배치 (20개)

- S1~S15 (물리 버튼 조합)
- Flick L/R/U/D
- Linear L/R/U/D
- Tilt L/R/U/D
- 각 트리거는 유일, 슬롯 순서 무관

### Tier B — 트리거 파라미터 조정

- 예: Flick 임계값을 슬롯별로 다르게
- 예: Long Click 임계값을 슬롯별로
- 복잡도 ↑, 실익 불확실

### Tier C — 새 트리거 정의

- 예: "Top L + Top R 동시 클릭"
- 예: "Side C 2초 + Side F 클릭"
- 조합 폭발, UX 혼란

권장: Tier A만. 트리거는 라이브러리, 슬롯은 자유 배정.

## 5. 검증 정책 (개별화의 필수 동반)

자유도 ↑ → 검증 필수. 놓치면 브릭.

| 검증 | 정책 | 
| --- | --- | 
| 트리거 중복 | 금지 | 
| 트리거 잠금 (하드코딩) | S1(Top L Hold), S5(Move Gate), S12(Mode Cycle), S13(Pairing) 유지 | 
| Action kind 유효 | 기존과 동일 | 
| Action 파라미터 범위 | 기존과 동일 | 
| Mode별 트리거 커버리지 | "최소 1개 트리거에 액션 할당" 권장 (경고만) | 
| 저장 전 검증 | 서버 + 클라이언트 이중 | 

UI 잠금 표시:

```
S1: [Top L Click 🔒] → [Mouse L Hold 🔒]
S5: [Top M Hold 🔒] → [Move Gate 🔒]
```

잠금 트리거는 슬롯 자체가 회색 + 자물쇠 아이콘.

## 6. Mode별 vs Global 개별화

질문: 사용자가 "S9를 모든 Mode에서 동일하게" 원하면?

**옵션**:

- (A) Mode별 독립 (현재) — 각 Mode에서 S9 개별 설정
- (B) Global 기본 + Mode 오버라이드 — Global 설정, 필요 시 Mode별 재정의
- (C) Global만 — 모든 Mode 동일

**트레이드오프**:

| 옵션 | 편의 | 유연성 | 
| --- | --- | --- | 
| A | 낮음 (3번 입력) | 최대 | 
| B | 중간 | 최대 | 
| C | 높음 | 낮음 | 

**권장: B (Global + 오버라이드). 이유**:
- "S9는 항상 Volume Up"이면 Global만 설정
- PPT Mode에서만 "S9 = PageDown"이면 오버라이드
- Config 구조: modes[n].slots[]가 비어있으면 global.slots[] 상속

단점: 상속 로직 + UI 표시("상속됨" vs "오버라이드됨") 추가.

## 8. Config 스키마 변화 (Option 1 채택 시)

현재:

```json
"slots": [
  { "k": 1, "h": 0, "p16": 1, "p32": 0 },   // index 0 = S1 (Top L Click 고정)
  ...
]
```

Option 1:

```json
"slots": [
  { "trig": 1, "k": 1, "h": 0, "p16": 1, "p32": 0 },   // 트리거 명시
  { "trig": 2, "k": 4, "h": 0, "p16": 43, "p32": 4 },
  ...
]
```

또는 배열 크기 = 트리거 개수:

```json
"slots": [
  { "k": 1, ... },   // index 0 = Trigger[0] (Top L Click)
  { "k": 4, ... },   // index 1 = Trigger[1] (Top L Double)
  ...
]
```

두 번째가 크기 절약. 트리거 순서를 고정 라이브러리로 정의.

트리거 순서 (제안):

```
0: Top L Click
1: Top L Double
2: Top L Long
3: Top M Click
4: Top M Hold (잠금)
5: Top R Click
6: Top R Double
7: Top R Long
8: Side F Click
9: Side F Long
10: Side C Click
11: Side C Double (잠금)
12: Side C 2s Hold (잠금)
13: Side R Click
14: Side R Long
15: Flick Left
16: Flick Right
17: Flick Up
18: Flick Down
19: Linear L
20: Linear R
21: Linear U
22: Linear D
23: Tilt L (Mode 3)
24: Tilt R
25: Tilt U
26: Tilt D
```

총 27개. 배열 index = 트리거 ID.

## 11. Mode별 vs Global (재확인)

Option 1 + Global 상속 (B안) 조합이 실질 최적:

- Global 슬롯 매트릭스 (27 트리거)
- 각 Mode는 오버라이드만 저장 (부분집합)
- 저장 크기 대폭 감소
- 사용자: "S9는 모든 Mode에서 Volume Up" 한 번 설정

Config 크기 절감:

- 현재: 3 Mode × 27 슬롯 = 81 (전부 저장)
- 상속: 27 + (오버라이드 × 3) ≈ 30~50
