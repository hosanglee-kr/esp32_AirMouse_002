

# 웹 기반 사용자 개별화 고도화 — 통합 설계 검토

## 0. 요구사항 정리

| 축 | 확정 사항 |
|---|---|
| **A. 프로파일 세트** | 다중 설정 (사용자/상황별) |
| **B. 매크로** | 액션 시퀀스 (다단 실행) |
| **D1. 자유도** | Option 1(slot중심) + 2(action중심) + 3(macro editor) 모두 |
| **D2. 트리거 라이브러리** | Tier A(기존 27) + 재검토 |
| **D3. 구조** | Global + Mode별 Override |
| **D4. 잠금** | S1/S5/S12/S13 유지 |
| **D5. Test** | Live Test |
| **D6. 마이그레이션** | 없음 (v0320 config 폐기) |

**핵심 난제:** 프로파일 × Global+Override × 매크로 × 3 UI view가 **동일 데이터의 다른 표현**이 되어야 함.

## 1. 아키텍처 결정 4개

### 1-1. 데이터 계층 (3층)

```
[Profile Layer]          5개 (Office / Gaming / Present / TV / Spare)
   │
   ├─ [Global Slots]     27 트리거 × Action  (모든 Mode 공통)
   │
   ├─ [Mode Overrides]   Mode별 예외 (override_mask로 표시)
   │
   ├─ [Macro Library]    Profile별 매크로 (최대 8개)
   │
   └─ [E10 Params]       DPI/감도/임계/Front Hold 등
```

**결정:** 프로파일이 완전한 설정 단위. 프로파일 전환 = 모든 것 스왑.

### 1-2. Global + Override 표현 (D3-B)

**문제:** Mode 3개 × 트리거 27개 × Action = 81슬롯. 그런데 대부분 Mode 공통.

**해결:** Global + Bitmask Override

```c
struct ST_C20_ProfileSlots_t {
    ST_C20_ActionSlot_t global[27];        // 모든 Mode 공통 (27 × 8 = 216B)
    ST_C20_ActionSlot_t modes[3][27];      // Mode별 override (216 × 3 = 648B, 실제 사용분만)
    uint32_t overrideMask[3];              // [mode] 각 27bit (or 32bit) — 12B
};  // ~880B
```

**규칙:**
```
slot(mode, trig) =
   if (overrideMask[mode] & (1 << trig))
       modes[mode][trig]
   else
       global[trig]
```

**잠금 트리거(S1/S5/S12/S13):** `global` 및 `modes[]`에 저장은 되나 UI에서 편집 불가.

### 1-3. 매크로 자료구조 (B)

```c
#define MAX_MACRO_STEPS   8
#define MAX_MACROS        8

struct ST_C20_MacroStep_t {
    uint8_t  kind;       // 1~9 (primitive만. 10=MACRO 금지: 중첩 방지)
    uint8_t  holdMode;   // 0=NONE, 1=PRESS (홀드 지속), 2=REPEAT
    uint16_t delayMs;    // 실행 전 대기 (0~2000)
    uint16_t param16;
    uint16_t _pad;
    uint32_t param32;
};  // 16 bytes

struct ST_C20_Macro_t {
    char     name[16];                       // 사용자 지정
    uint8_t  stepCount;                      // 1~8
    uint8_t  _pad[3];
    ST_C20_MacroStep_t steps[MAX_MACRO_STEPS];
};  // 16 + 4 + 128 = 148 → align 148

struct ST_C20_MacroLib_t {
    uint8_t  count;                          // 0~8
    uint8_t  _pad[3];
    ST_C20_Macro_t macros[MAX_MACROS];
};  // 4 + 8×148 = 1188B ≈ 1.2KB
```

**매크로 실행:**
```
1. commTask가 slot.kind == MACRO 받음
2. param32 = macro index
3. macro의 step 순회:
   - delayMs 대기
   - step 실행 (primitive)
   - repeat/hold 처리
4. 시퀀스 완료
```

**매크로 중 취소:** 진행 중 ForceRelease 또는 Mode 전환 시 abort flag.

### 1-4. Action 표현 확장

**기존 `ST_C20_ActionSlot_t` (8B) 유지 + kind 확장:**

```c
enum EN_C20_ActionKind_t : uint8_t {
    EN_C20_ACT_NONE            = 0,
    EN_C20_ACT_MOUSE_CLICK     = 1,
    EN_C20_ACT_MOUSE_HOLD      = 2,
    EN_C20_ACT_MOUSE_WHEEL     = 3,
    EN_C20_ACT_KB_TAP          = 4,
    EN_C20_ACT_KB_COMBO        = 5,
    EN_C20_ACT_KB_REPEAT       = 6,
    EN_C20_ACT_CONSUMER_TAP    = 7,
    EN_C20_ACT_CONSUMER_REPEAT = 8,
    EN_C20_ACT_SPECIAL         = 9,
    EN_C20_ACT_MACRO           = 10,   // 신규: param32 = macro index

```

**변경 없음.** `param32`가 macro index로 해석될 뿐. 하위호환 + 크기 동일.

## 4. Global + Override 메커니즘

### 4-1. 저장 최적화

**Override 최소화 원칙:**
- Global에 모든 값 저장 (default)
- Mode별 차이만 override
- `override_mask`로 표시

**예시:**
```
Global: S9 = Volume Up (모든 Mode)
Mode 2: S9 = PageDown (PPT 전용)
→ global[9] = Volume Up
→ override_mask[1] |= (1<<9)
→ modes[1].slots[9] = PageDown
```

### 4-2. 런타임 조회

```c
ST_C20_ActionSlot_t _resolveSlot(uint8_t p_mode, uint8_t p_trig) {
    const uint8_t m = p_mode - 1;   // 1~3 → 0~2
    if (_profile.overrideMask[m] & (1u << p_trig)) {
        return _profile.modes[m].slots[p_trig];
    }
    return _profile.global[p_trig];
}
```

**O(1).** 조회 부담 없음.

### 4-3. UI 표시

```
┌────────────────────────────────────────────┐
│ Mode 1 (PC) 편집 중  [Global 상속 표시]     │
├────────────────────────────────────────────┤
│ S1  🔒 Top L Click → Mouse L Hold (잠금)   │
│ S2  [G] Top L Double → Alt+Tab             │
│ S3  [G] Top L Long → (없음)                │
│ ...                                        │
│ S9  [M1] Side F Click → Volume Up ← 오버라이드 │
│ ...                                        │
└────────────────────────────────────────────┘

[G] = Global 상속
[M1] = Mode 1 오버라이드
```

**토글:** "Global로 되돌리기" 버튼 → override 삭제.

## 5. 실행 흐름

### 5-1. sensorTask (버튼/제스처)

```
_onBtnEvent / _handleGesture
  ↓
_resolveSlot(_activeMode, trigger)
  ↓
if (kind == SPECIAL):
    _handleSpecial() 즉시 (sensorTask)
else if (kind == MACRO):
    _enqueueAction(slot, isDown)   // commTask가 매크로 시퀀서 실행
else:
    _enqueueAction(slot, isDown)
```

### 5-2. commTask (Action 실행)

```
_qActionExec drain
  ↓
_actExec.exec(slot, isDown)
  ↓
if (kind == MACRO):
    _runMacro(macroIndex)    // 신규
else:
    (기존 실행)
```

**`_runMacro` (신규):**
```cpp
void _runMacro(uint8_t p_macroIdx) {
    if (p_macroIdx >= _macroLib.count) return;
    const ST_C20_Macro_t& m = _macroLib.macros[p_macroIdx];

    _macroAbort = false;

    for (uint8_t i = 0; i < m.stepCount; i++) {
        if (_macroAbort) break;

        const ST_C20_MacroStep_t& s = m.steps[i];
        if (s.delayMs > 0) {
            // abort 가능한 delay
            const uint32_t t0 = millis();
            while ((millis() - t0) < s.delayMs) {
                if (_macroAbort) break;
                vTaskDelay(pdMS_TO_TICKS(10));
            }
        }

        // primitive 실행 (SPECIAL 제외)
        ST_C20_ActionSlot_t slot = {s.kind, s.holdMode, s.param16, s.param32};
        _execPrimitive(slot, true);
    }
}
```

**주의:** 매크로 중 `Mode 전환`, `ForceRelease`, BLE disconnect → `_macroAbort = true`.

### 5-3. Profile 전환

```
1. 진행 중 액션/repeat 해제 (`_actExec.releaseAll()`)
2. 매크로 abort (`_macroAbort = true`)
3. 디스패처/제스처 리셋
4. ForceRelease
5. 신규 프로파일 로드 (LittleFS)
6. `_applyE10ToRuntime`
7. LED: 흰색 3회 flash
8. active_profile.json 저장
```

## 6. Web UI 3-View 설계

### 6-1. View 1 — Slot-centric (기존 Mode Slots 탭 확장)

**레이아웃:**
```
[Profile: Office ▼]  [Mode: 1 | 2 | 3]  [Global 보기]

┌────────────────────────────────────────────┐
│ 트리거              │ Action                 │
├────────────────────────────────────────────┤
│ S1  🔒 Top L Click  │ [Mouse L Hold    ] 🔒 │
│ S2    Top L Double  │ [Alt+Tab         ▼] [G]│
│ S3    Top L Long    │ [없음            ▼] [G]│
│ ...                                        │
│ S9  [M1] Side F Click│ [Volume Up      ▼] [M1]│
└────────────────────────────────────────────┘
```

**기능:**
- Action select: 프리셋 + 매크로 + NONE
- [G]/[M1] 배지: Global vs Override
- 우클릭 or 버튼: "Global로 되돌리기"
- 잠금 트리거: 회색 + 자물쇠

### 6-2. View 2 — Action-centric (신규 탭 "Action Map")

**레이아웃:**
```
[Action 검색: ____]

┌────────────────────────────────────────────┐
│ Action             │ 할당된 트리거           │
├────────────────────────────────────────────┤
│ Mouse L Hold       │ S1 (Global, 잠금)      │
│ Mouse R Click      │ S6 (Global)            │
│ Alt+Tab            │ S2 (Global)            │
│ PageDown           │ S1 (Mode 2 override)   │
│ Volume Up          │ S9 (Global)            │
│ 매크로: Ctrl+C→V   │ 없음                   │
│ ...                                        │
└────────────────────────────────────────────┘
```

**기능:**
- 각 액션 옆 [재할당] 버튼 → 트리거 선택 다이얼로그
- 액션 검색/필터
- 미할당 매크로 강조

### 6-3. View 3 — Macro Editor (신규 탭 "Macros")

**레이아웃:**
```
[매크로 목록]
  • Ctrl+C → V
  • Alt+Tab x2
  • Win+D → Wait → Win+D
  [+ 새 매크로]

[편집: Ctrl+C → V]
  Step 1: [KB Tap ▼] [LCtrl ▼] [C ▼]  delay: 0 ms    [×]
  Step 2: [KB Tap ▼] [LCtrl ▼] [V ▼]  delay: 100 ms  [×]
  [+ Step 추가]

  이름: [Ctrl+C → V]
  [저장] [삭제] [Live Test]
```

**기능:**
- Step 추가/삭제/순서 변경
- 각 Step별 kind 선택 → 파라미터 UI (기존 슬롯 편집기 재사용)
- Live Test: 매크로 즉시 실행 (BLE 연결 시)

### 6-4. 공통 UI 요소

- **Profile 관리 바** (모든 탭 상단):
  ```
  Profile: [Office ▼] [전환] [복제] [이름변경] [삭제]
  ```
- **Live Test 버튼** (Action/Macro 편집 시):
  - `POST /api/action/test {kind, p16, p32, holdMs}` → HID 전송
  - 매크로는 `{steps: [...]}` 형태

## 8. 검증/안전장치

### 8-1. 트리거 잠금

```c
static constexpr bool G_TRIG_LOCKED[27] = {
    true,  false, false, false, true,   // S1, S5
    false, false, false, false, false,
    false, true,  true,  false, false,  // S12, S13
    false, false, false, false,
    false, false, false, false,
    false, false, false, false
};
```

**서버 검증:** 잠금 트리거 편집 시도 → reject.
**클라이언트:** UI에서 disabled.

### 8-2. 매크로 검증

- Step 0~7 (최대 8)
- 각 Step kind 1~9 (MACRO 제외 — 중첩 방지)
- `delayMs` 0~2000
- 이름 16자
- 매크로 개수 0~8

### 8-3. 슬롯 검증

- Action kind 0~10
- MACRO 참조 시 index < `macroLib.count`
- 기타 기존 규칙 유지

### 8-4. 프로파일 검증

- 개수 1~5
- 이름 16자
- 각 프로파일 저장 시 `validateProfile()`
- 활성 프로파일 존재 보장

### 8-5. Cross-cutting

- 프로파일 전환 중 저장 시도 → 거부 (진행 중 플래그)
- 매크로 실행 중 편집 → 다음 실행부터 반영

## 9. 마이그레이션 정책 (D6)

**v0320 config (`config_0400.json`) 폐기.**

**부팅 시 동작:**
1. `/json/profiles/` 디렉토리 없음 → 새 구조로 초기화
2. `profile_0.json` 없음 → `makeDefaultsProfile(0)` 저장
3. `active_profile.json` 없음 → `{active_index: 0, profile_count: 1}` 저장
4. 기존 `config_0400.json` 있으면 → **무시** (삭제 안 함, 참고용 보존)
5. 사용자가 원하면 FactoryReset으로 정리

**장점:** 마이그레이션 로직 불필요. 코드 단순.

# 결정 필요 사항 (R1~R10) 상세 설명

## R1. 매크로 최대 개수

**무엇을 결정?** 프로파일 하나당 저장 가능한 매크로 개수 상한.

| 옵션 | LittleFS | 실사용 |
|---|---|---|
| **8** | 8 × 148B = 1.2 KB | 대부분 충분 |
| 16 | 16 × 148B = 2.4 KB | 헤비 유저 |

**영향:**
- 저장공간: 미미 (LittleFS 여유 1.5 MB)
- Config body: 매크로 JSON 크기 증가
- UI: 목록 길이

**실사용 관점:**
- "복사/붙여넣기", "창 전환", "스크린샷" 등 **자주 쓰는 3~5개**면 충분
- 8개 이상은 사용자가 관리 못 함

**권장: 8.** 이유:
- LittleFS/UI 부담 최소
- 실제 사용 패턴상 8개면 충분
- 부족하면 v5.1에서 상향 가능

---

## R2. 매크로 최대 step

**무엇을 결정?** 매크로 하나에 들어갈 최대 액션 개수.

| 옵션 | 매크로 크기 | 시나리오 |
|---|---|---|
| **8** | 8 × 16B = 128B | 대부분 매크로 커버 |
| 16 | 16 × 16B = 256B | 복잡한 시퀀스 |

**영향:**
- 매크로 실행 시간 (step당 ~30ms + delay)
- 8 step × 100ms delay = ~1초
- 16 step이면 2초+ → UX 저하

**실사용 관점:**
- 일반 매크로: 2~4 step (예: Ctrl+C → delay → Ctrl+V)
- 복잡한 것: 6~8 step
- 16 step은 거의 없음

**권장: 8.** 이유:
- 실사용 커버
- UI 편집 부담 (16 step은 스크롤 지옥)
- Config 크기

---

## R3. 매크로 step delay 최대

**무엇을 결정?** 각 step 사이 대기시간 상한.

| 옵션 | 시나리오 |
|---|---|
| 500ms | 빠른 시퀀스 (연타) |
| **2000ms** | 일반 (앱 로딩 대기 등) |
| 5000ms | 앱 시작 대기 |

**영향:**
- 500ms: "Ctrl+C → 즉시 Ctrl+V" 같은 초고속 매크로엔 충분
- 2000ms: "앱 실행 → 1.5초 대기 → 추가 동작" 가능
- 5000ms: "브라우저 열기 → 페이지 로드 대기 → 클릭"

**UX 리스크:**
- 긴 delay 중 취소 안 되면 사용자 답답
- R7(취소 경로)과 연동됨

**권장: 2000ms.** 이유:
- 500ms는 "앱 로딩 대기" 같은 시나리오 불가
- 5000ms는 오버킬 + 취소 UX 필수
- 2000ms가 균형

**대안:** "장시간 대기"는 별도 step kind (`WAIT_MS` 확장)로 분리 가능. 지금은 delay로 통합.

---

## R4. 프로파일 개수

**무엇을 결정?** 저장 가능한 프로파일 최대 개수.

| 옵션 | LittleFS | 사용자 관리 |
|---|---|---|
| 3 | ~12 KB | 매우 단순 |
| **5** | ~20 KB | 적정 |
| 10 | ~40 KB | 과부하 |

**영향:**
- LittleFS: 미미 (여유 1.5 MB)
- UI: 프로파일 select 목록 길이
- 관리 부담: 이름 짓기, 복제/삭제

**실사용 관점:**
- 3개: "업무 / 개인 / 발표" 정도
- 5개: "업무 / 게임 / 발표 / TV / 임시"
- 10개: 관리 못 함

**권장: 5.** 이유:
- 사용자 시나리오 4~5개가 자연스러움
- LittleFS 여유
- UI 부담 적정

**주의:** 프로파일 개수 상한은 **고정값**. 동적 확장 없음 (재부팅 후 유지).

## R5. 프로파일 전환 트리거

**무엇을 결정?** 프로파일을 어떻게 전환?

| 옵션 | 장점 | 단점 |
|---|---|---|
| **웹 UI만** | 단순, 실수 없음 | 폰/PC 접속 필요 |
| **버튼 조합** | 즉시 전환 | 조합 충돌, 학습 필요 |
| **Mode 연동** | 자동 | 예측 어려움 |

**버튼 조합 채택 시 후보:**
- Side R 3초 + Top R 클릭
- Side C 3초 + Top R 클릭 (Host Cycle과 유사)
- Top L + Top R 동시 클릭

**문제:**
- 이미 Host Cycle(Side C 3초 + Top L)이 있음
- 추가 조합은 사용자 혼란
- 실수 전환 → 예상치 못한 Mode/Action

**웹 UI만 채택 시:**
- 폰으로 접속해서 전환 (편함)
- 프로파일 이름이 화면에 보여 실수 없음
- Mode 자체는 기존처럼 버튼으로 (프로파일과 독립)

**권장: 웹 UI만 (초기).** 이유:
- 안전 (실수 방지)
- UX 명확
- 버튼 조합은 v5.1에서 추가 가능

**대안:** "프로파일별 Mode 지정" — 프로파일 전환 시 Mode도 함께 변경. 예: Office → Mode 1, Present → Mode 2.

## R6. Live Test 안전장치

**무엇을 결정?** 슬롯/매크로 편집 중 "테스트" 버튼 동작.

| 옵션 | 시나리오 |
|---|---|
| **확인 다이얼로그** | "정말 실행?" 팝업 |
| 즉시 | 클릭 = 즉시 실행 |

**영향:**
- 확인 다이얼로그: 안전, 클릭 2회
- 즉시: 빠름, 실수 시 의도치 않은 HID

**실사용 관점:**
- 편집 중 여러 번 테스트 → 다이얼로그 짜증
- "실수로 Ctrl+Alt+Del 실행" 같은 사고 방지 필요

**권장: 확인 다이얼로그.** 이유:
- 실수 방지 우선
- 편집 중 여러 번 테스트해도 5초 정도 손해
- 매크로(Live Test)는 강한 경고 (예: "매크로 8 step 실행됨")

**대안:** 첫 1회만 다이얼로그, 이후 5분간 자동 실행 허용. 복잡하므로 v5.0엔 단순하게.

## R7. 매크로 중 취소 경로

**무엇을 결정?** 매크로 실행 중 사용자가 어떻게 중단?

| 옵션 | 시나리오 |
|---|---|
| **자동만** | Mode 전환/disconnect 시 abort |
| 취소 버튼 | 명시적 취소 (웹 or 물리 버튼) |

**자동 취소 트리거:**
- Mode 전환 (Side C 더블)
- ForceRelease (`/api/control`)
- BLE disconnect
- SafeMode/OTA Guard 진입

**취소 버튼 후보:**
- 물리: 특정 버튼 (예: Top M 3초 hold)
- 웹: "매크로 중단" 버튼

**UX 관점:**
- 매크로가 2초 이상 실행되면 취소 필요
- 매크로 8 step × 200ms = 1.6초 → 드물게 취소 필요
- 물리 버튼이 직관적

**권장: 자동만 (초기).** 이유:
- 짧은 매크로엔 취소 불필요
- 취소 경로 추가 시 매크로 중 다른 버튼 눌림 → 오작동 위험
- 실사용 후 필요하면 v5.1에서 "Top M 3초 hold = abort" 추가

**주의:** 자동 취소는 반드시 있어야 함 (진행 중 stuck 방지). R7의 "자동만"도 최소한 이건 포함.

## R8. Global vs Override UI 표시

**무엇을 결정?** 사용자가 "이 슬롯이 Global인지 Override인지" 어떻게 알까?

| 옵션 | 시각 |
|---|---|
| **배지** | [G] / [M1] 텍스트 배지 |
| 상속 아이콘 | ⬆ / ● 같은 아이콘 |
| 색상 | 배경색 차이 |
| 조합 | 배지 + 색상 |

**각 방식:**
- **배지**: 명확, 텍스트라 학습 쉬움. 공간 차지
- **아이콘**: 공간 절약. 학습 필요
- **색상**: 즉각 인지. 색맹 사용자 문제
- **조합**: 최선. 복잡

**실사용 관점:**
- 사용자가 "이 Mode에서 이 슬롯 다르게 동작하는구나" 인지 필수
- 배지가 가장 명확
- "Global로 되돌리기" 버튼도 필요

**권장: 배지 + 색상 조합.** 예:
- Global: 회색 배경 + "[G]" 배지
- Mode Override: 파란 배경 + "[M1]" 배지
- 잠금: 어두운 회색 + 🔒

**이유:**
- 색상으로 즉각 인지
- 배지로 정확한 정보
- 접근성 (색맹 사용자도 텍스트로 구분)

## R9. 기존 `/api/ppt` 처리

**무엇을 결정?** v0400의 `/api/ppt?mode=N` 엔드포인트를 어떻게?

| 옵션 | 영향 |
|---|---|
| 유지 | v0400 웹 앱과 하위호환 |
| 폐기 | API 단순화, v0400 앱 수정 필요 |

**v0400에서의 역할:**
- Mode 슬롯 매트릭스 조회/저장
- 웹 UI Mode Slots 탭의 백엔드

**v5.0에서의 역할:**
- 프로파일 시스템이 대체
- `/api/profiles/{idx}` + `/api/slots/*` 로 대체 가능

**영향:**
- **유지**: v0400 웹앱이 v5.0 펌웨어에서도 동작 (활성 프로파일의 모드 슬롯 조회/저장으로 매핑)
- **폐기**: v0400 웹앱 사용 불가 → v5.0 웹앱 강제

**실사용 관점:**
- 어차피 v5.0 웹앱을 배포
- 기존 v0400 웹앱은 프로파일 개념 없음 → 혼란
- **폐기가 명확**

**권장: 폐기.** 이유:
- v5.0 웹앱이 유일한 UI
- API 일관성 (프로파일 중심)
- 유지보수 부담 감소

**대안:** v5.0에서도 `/api/ppt`가 활성 프로파일의 Mode 슬롯을 조회/저장하도록 **호환 계층** 제공. 하지만 실익 낮음.

## R10. 기존 `config_0400.json` 처리

**무엇을 결정?** v0400에서 쓰던 config 파일을 v5.0 부팅 시 어떻게?

| 옵션 | 시나리오 |
|---|---|
| **무시 보존** | 파일 그대로 두고 프로파일 시스템으로 초기화 |
| 자동 삭제 | 부팅 시 삭제 |
| 자동 마이그레이션 | v0400 → v5.0 profile_0 변환 |

**각 방식:**
- **무시 보존**: 안전. 사용자가 이전 설정 참고 가능
- **자동 삭제**: LittleFS 정리. 이전 설정 소실
- **자동 마이그레이션**: 편함. 마이그레이션 로직 복잡

**실사용 관점:**
- 사용자가 이전 설정을 그대로 쓰고 싶어 함
- 마이그레이션 로직은 v5.0 코드 부담 (특히 매크로 없음 → 있음 변환)
- D6 확정: **미고려, v0320 config 폐기**

**권장: 무시 보존.** 이유:
- D6 확정과 일치 (폐기 = 사용 안 함)
- 파일 삭제는 사용자 판단 (FactoryReset)
- 참고용으로 남겨두면 사용자가 수동 참조 가능

**실제 동작:**
1. 부팅 시 `profiles/` 없음 → 새로 생성
2. `config_0400.json` 있으면 그냥 무시 (삭제 안 함)
3. 사용자가 새 프로파일 설정
4. 원하면 `/api/factory_reset`으로 정리
